## O que ainda machuca a primeira impressão

### 1. Três CLIs diferentes, sem indicação de qual é o oficial

| Arquivo | O que é |
|---|---|
| `src/cli/runner.py` | O documentado em `CLAUDE.md` (`python src/cli/runner.py run/start`) — **este é o canônico** |
| `quantum.py` | Wrapper fino que importa `cli.runner.main` — redundante com o de cima |
| `quantum_cli.py` | CLI **completamente diferente** ("Phase C: Developer Experience" — `create`, `dev`, `build`, `init`, `inspect`) — comandos que não existem no `runner.py` |
| `./quantum` (shell script) | Chama `quantum_cli.py`, não `quantum.py` nem `runner.py` — ou seja, o wrapper "canônico" de nome chama o CLI **não documentado** |

Um novo usuário rodando `./quantum` cai no CLI errado (o não documentado). Isso precisa de
uma decisão sua, não uma limpeza automática: **`quantum_cli.py` tem comandos
(`create`/`dev`/`build`/`init`) que `runner.py` não tem — são funcionalidades que você
ainda quer, ou ficaram para trás?** Dependendo da resposta, ou elas migram para
`runner.py` e os outros três arquivos somem, ou `quantum_cli.py` vira o canônico e
`runner.py`/`quantum.py` é que ficam redundantes.

### 2. Artefatos de build commitados como se fossem código-fonte

Confirmei abrindo os arquivos — os cabeçalhos se denunciam:

| Arquivo | Cabeçalho confirma |
|---|---|
| `llm-chat.py` | `"Generated by Quantum Terminal Engine"` |
| `task-manager.py` | `"Generated pywebview Application... generated by the Quantum UI Engine"` |
| `dungeon-quest.py`, `file-browser.py`, `task-manager-tui.py`, `server-dashboard.py`, `dashboard.py` | Mesmo padrão de nome/propósito (saída de `compile_game.py`/motor de UI/terminal a partir de `.q` em `examples/`) — não abri todos, mas a hipótese é forte dado o padrão dos dois confirmados |

Isso é saída de compilação, versionada como se fosse fonte. Regenerável a qualquer momento
rodando o compilador contra o `.q` correspondente em `examples/`. Não deveria estar no
controle de versão — deveria estar no `.gitignore` (como `*.generated.py` ou uma pasta
`dist/`/`build/` dedicada), com um `Makefile`/script que os regenera quando necessário para
demo.

### 3. Ferramentas de teste paralelas ao pytest

`test_runner.py` (raiz) é um regression runner customizado, coexistindo com a suíte
`pytest` real em `tests/` + `pytest.ini` + `tests/conftest.py`. Mais `conftest.py`,
`test_database.py`, `test_query.py` soltos na raiz — nomes que fazem parecer testes pytest,
mas fora do diretório `tests/` (pytest pode até coletá-los da raiz dependendo do
`pytest.ini`, o que é uma fonte de confusão a mais). Se `test_runner.py` já não é usado,
vira uma pergunta de "docs/archive/" do outro plano; se ainda é, merece virar
`scripts/test_runner.py` com essa distinção clara no nome.

### 4. Metadado desatualizado que não é `.md`

`package.json:4`: `"description": "> 🧠 Codename: FF / FireFusion > ⚡ Status: Initial Runner implementation"` — para um projeto com 30 features, IA e game engine. Mesma doença do
`ROADMAP.md`, só que em JSON, então nenhuma das buscas por `.md` desta sessão o pegou.

### 5. Coisas pequenas

mais "profissional", mas é uma mudança de maior risco (paths relativos, imports, CI, se
houver) para um ganho principalmente estético. **Recomendo não mexer nisso agora** — o
ganho de "parecer projeto final" está muito mais na raiz suja do que nesses quatro
diretórios já organizados.
