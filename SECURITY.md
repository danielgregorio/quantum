# Security Policy

Quantum is pre-1.0 experimental software. We take security seriously, especially because
the language evaluates expressions and renders user-facing output.

## Reporting a vulnerability

**Please do not report security issues in public GitHub issues.**

Instead, report privately via one of:

- GitHub's [private vulnerability reporting](https://github.com/danielgregorio/quantum/security/advisories/new) (preferred), or
- email to **danielgregorio2611@gmail.com** with the subject `[SECURITY] Quantum`.

Please include:

- A description of the vulnerability and its impact.
- A minimal `.q` file or steps that reproduce it.
- Any suggested remediation, if you have one.

We aim to acknowledge reports within **72 hours** and to provide a remediation timeline
after triage.

## Scope & known limitations

Because Quantum is experimental, treat it accordingly:

- **Do not expose a Quantum app to untrusted input in production** until you have reviewed
  the data path yourself.
- Expression evaluation, output rendering (XSS), `q:query` (SQL), and `q:action` (CSRF) are
  active hardening areas. If you find a sandbox escape or injection, that is exactly the
  kind of report we want.
- Never commit secrets (API keys, tokens) to the repo. Configure them via environment
  variables (e.g. `QUANTUM_API_KEY`).

### `q:python` is a full-trust escape hatch

`q:python`, `q:pyclass` and `q:pyimport` execute arbitrary Python **in the server
process, with no sandbox** — full access to the filesystem, the network, and `os`.
That is intentional: it is the escape hatch for things the declarative tags cannot
express, and it is no more privileged than the Python code of the app itself.

The boundary that matters is *who wrote the code that reaches it*. It is safe for
templates you wrote. It is not safe for any template you did not write — anything
generated by an LLM, submitted by a user, or pulled from an untrusted source.

Turn it off for those cases:

```yaml
# quantum.config.yaml
security:
  python_scripting: false   # q:python / q:pyclass / q:pyimport refuse to run
                            # (this is the DEFAULT — omitting the key
                            #  means off. Set true only for code you
                            #  wrote yourself.)
```

Any feature that lets a model generate or select template content must disable it
first. An allowlist was considered and rejected: real usage imports `json`, `csv`,
`collections`, `statistics` and `functools`, so an allowlist permissive enough to
be usable would not be a real boundary — and a boundary that looks stronger than it
is, is worse than an honest switch.

The switch covers **four** execution sites, not the three tags above: a `q:python`
block nested inside a `q:action` runs through `ActionHandler._execute_python`,
which has its own `exec()`. That path did not check the flag when the switch was
introduced, so setting `python_scripting: false` could be walked around by moving
the block inside an action — a switch that does not switch everything off is worse
than none, because the operator believes they are covered. Fixed and pinned by
`tests/unit/test_python_scripting_policy.py::TestTheSwitchCannotBeWalkedAround`.

If you add another place that runs author-supplied Python, it must call
`require_python_scripting()` (executors) or check
`services.python_scripting_enabled` directly.

## Supported versions

Until 1.0, only the latest `main` receives security fixes.
